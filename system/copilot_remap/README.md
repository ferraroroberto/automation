# Copilot Key Remap

Restores the physical key that Windows now treats as the **Copilot key** back to
behaving like a regular **Ctrl** — including hold behavior, so combos like
`Ctrl+C`, `Ctrl+V`, `Ctrl+S` all work.

> **PC-specific.** This setup is configured for **this machine only**
> (user `rober`, paths under `E:\automation\automation\`, the venv at
> `.venv\Scripts\pythonw.exe`). Re-run `detect` and `install_autostart.ps1` on
> any other PC.

---

## Why this is needed

On this laptop the right-Ctrl was reflashed in firmware/driver to send the
Windows Copilot key. The Copilot key does **not** emit a single scancode —
it sends a **chord**: `LWin + LShift + F23` (verified by the detector).
That means a registry `Scancode Map` cannot fix it; the remap has to happen
at runtime by intercepting and rewriting the chord.

This is what the script does, using a Win32 **low-level keyboard hook**
(`SetWindowsHookEx WH_KEYBOARD_LL`) and `SendInput`. Pure stdlib — no
third-party Python packages.

---

## What was set up

1. **Detection** — `copilot_remap.py detect` recorded what the Copilot key
   actually sends on this hardware. The detected chord (`LWin + LShift + F23`)
   was saved to [`chord.json`](chord.json) along with the target VK
   (`VK_RCONTROL` = 0xA3, i.e. Right Ctrl).

2. **Runtime remapper** — `copilot_remap.py run` installs the hook and
   rewrites the chord into a real Right-Ctrl press, holding it for as long as
   you hold the physical key. Injected events are tagged via `dwExtraInfo`
   so the hook ignores its own output.

3. **Autostart** — `install_autostart.ps1` registers a per-user **Scheduled
   Task** named `RemapCopilotKey` that runs the script at every logon, hidden
   (via `pythonw.exe`, so no console window appears).

   ```
   Trigger : MSFT_TaskLogonTrigger (AtLogOn, UserId=LAPTOP\rober)
   Action  : E:\automation\automation\.venv\Scripts\pythonw.exe
             "E:\automation\automation\system\copilot_remap\copilot_remap.py" run
   Settings: ExecutionTimeLimit=0 (no limit), MultipleInstances=IgnoreNew,
             AllowStartIfOnBatteries=True
   Principal: rober, Interactive, Limited (no admin needed)
   ```

## How the hook handles the chord

The driver sends `LWin + LShift + F23` as three rapid key-down events when you
press the Copilot key, and the matching three key-ups when you release it.
Naively suppressing only F23 would leave the OS thinking `Win+Shift` was held,
which corrupts the resulting Ctrl combo.

The hook handles it like this:

1. On `F23` **down** (with `LWin` and `LShift` already pressed): inject
   key-up events for `LWin` and `LShift` to cancel the spurious modifier
   state, then inject `RCtrl` **down**. Suppress the `F23` event.
2. While the key is held, real keystrokes (e.g. `C`) reach the OS as
   `RCtrl + C`.
3. On `F23` **up**: inject `RCtrl` **up** and suppress the event.
4. The driver then sends `LWin` up and `LShift` up; the hook swallows them
   too, since the OS already considers them released.

## Day-to-day commands

```powershell
# Run now / stop now (without reboot)
Start-ScheduledTask -TaskName RemapCopilotKey
Stop-ScheduledTask  -TaskName RemapCopilotKey

# Status
Get-ScheduledTask   -TaskName RemapCopilotKey | Get-ScheduledTaskInfo

# See the running process(es)
Get-CimInstance Win32_Process -Filter "Name='pythonw.exe'" |
    Where-Object { $_.CommandLine -like "*copilot_remap*" } |
    Select-Object ProcessId, CommandLine
```

> Note: you'll typically see **two** `pythonw.exe` processes — the venv's
> `pythonw.exe` is a thin pyenv launcher that spawns the actual Python
> interpreter (parent → child). The keyboard hook lives in the child.

## Reinstall / change

```powershell
# Re-detect the chord (e.g. after a driver/firmware change)
& "e:\automation\automation\.venv\Scripts\python.exe" `
  "e:\automation\automation\system\copilot_remap\copilot_remap.py" detect

# Show what's currently saved
& "e:\automation\automation\.venv\Scripts\python.exe" `
  "e:\automation\automation\system\copilot_remap\copilot_remap.py" show

# Re-register the task (idempotent — uses -Force)
& "e:\automation\automation\system\copilot_remap\install_autostart.ps1"
```

To change the target key (e.g. Left Ctrl instead of Right Ctrl), edit
`chord.json` directly:

| Target | `target_vk` |
|--------|-------------|
| Right Ctrl | `163` (0xA3) |
| Left Ctrl  | `162` (0xA2) |
| Generic Ctrl | `17` (0x11) |

Then `Stop-ScheduledTask` + `Start-ScheduledTask` to pick up the change.

---

## Uninstall (full removal)

```powershell
& "e:\automation\automation\system\copilot_remap\uninstall_autostart.ps1"
```

This stops any running instance, unregisters the Scheduled Task, and kills any
lingering `pythonw.exe` running the script. Files in this folder are left in
place — delete the folder yourself if you don't want them.

## Caveats / known edge cases

- **Holding Shift legitimately when tapping the Copilot key** — the hook will
  release the Shift you were holding. Rare in practice; not handled.
- **Win+Shift during the chord** — there's a sub-millisecond window between
  the driver's `LWin`/`LShift` down and the `F23` down where the OS technically
  sees Win+Shift held. The hook cancels this immediately on `F23` down, so no
  app should ever react. If you observe Start menu flashes or accessibility
  shortcuts firing, flag it.
- **Admin processes** — Windows blocks user-level keyboard hooks from
  intercepting keys typed into elevated (admin) windows. Inside an admin
  console / app, the Copilot key will revert to launching Copilot.
  Workaround would be to run the remapper itself elevated (would need to
  change `install_autostart.ps1` to `RunLevel Highest`).
